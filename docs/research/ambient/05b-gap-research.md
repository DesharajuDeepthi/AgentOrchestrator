## Area 1 — Agent-self-managed heartbeats and self-scheduling

### 1.1 The agent schedules its own next wakeup

**Claude Code `ScheduleWakeup` / dynamic `/loop`.** Claude Code 2.1.x added a `ScheduleWakeup` tool: at the end of each loop iteration the model itself chooses when to be resumed — a specific time, a delay, or `stop: true` to end the loop ([changelog note](https://x.com/ClaudeCodeLog/status/2042685462909685820), [mechanics write-up](https://zenn.dev/ai_eris_log/articles/claude-code-schedule-wakeup-20260519?locale=en), [scheduled-tasks docs](https://code.claude.com/docs/en/scheduled-tasks)). Key properties:

- The `/loop` skill with **no interval argument** = self-paced mode: the model passes the same loop prompt back to itself with a chosen delay ("build running → check in 2 min; nothing happening → check in 30 min").
- With an explicit interval, pacing is fixed and the model only decides *content*, not cadence.
- Failure modes are instructive: [issue #58235](https://github.com/anthropics/claude-code/issues/58235) — no cancellation mechanism meant re-scheduling on every wakeup could create runaway loops; [issue #51304](https://github.com/anthropics/claude-code/issues/51304) — a wakeup re-entering a slash command on an already-completed task. Lesson: self-scheduling needs (a) an explicit cancel/stop verb, (b) a "task already done" guard at wake time, (c) a cap on total wakeups.

**MemGPT/Letta `request_heartbeat`.** In MemGPT/Letta every action is a tool call, and the runtime injects an extra keyword argument `request_heartbeat: bool` (default `false`) into **every tool schema**. Setting it `true` tells the server "run me again after this tool returns" — i.e., the LLM itself decides whether the loop continues ([Letta heartbeats guide](https://docs.letta.com/guides/agents/heartbeats), [legacy MemGPT agent docs](https://docs.letta.com/guides/legacy/memgpt_agents_legacy), [Letta v1 agent-loop retrospective](https://www.letta.com/blog/letta-v1-agent/)). Two details worth stealing:

- On **tool failure, the server auto-generates a heartbeat** so the agent gets a turn to observe the error and retry/adapt — the loop never dies silently on an exception.
- The heartbeat is a *request*, arbitrated by the server (step caps still apply) — the model proposes, the harness disposes. That's the right trust boundary for self-pacing: agent picks the interval, platform clamps it to `[min, max]` and enforces budgets.

**AutoGPT/BabyAGI** are the negative baseline: unpaced `while True` loops that burn tokens continuously with no notion of "nothing to do, sleep longer." The whole self-pacing literature exists because of that failure mode.

### 1.2 PM-Bench: what the heartbeat condition actually was and why it won

[PM-Bench (arXiv:2607.12385)](https://arxiv.org/html/2607.12385v1) evaluates *prospective memory* — deferred intentions ("do X when Y happens / at time T") across a simulated 7-day week, 83 tasks with time-based and event-based triggers, under distraction. Conditions:

- **Automatic heartbeat (30 or 60 virtual minutes):** the harness injects a periodic nudge that *lists channels worth checking* but does **not** reveal the hidden cues. 30-min variant: best on monitoring-required slices — **60.4%** on clock-monitoring tasks, **15.8%** on hidden-channel tasks — but **489 false positives** and only **57.8% macro Set-F1**.
- **Optional heartbeat:** the agent may emit `set_heartbeat` to enable/disable its own 30- or 60-min nudge. Slightly lower monitoring hit rates (54.7% clock, 10.0% hidden) but the **best overall Set-F1 (65.1%)** and the best cross-day result (**50.0%** hit rate).

Why it matters: (1) any periodic wake beats pure reactivity for time-triggered obligations (clock hit rate ~46% → 55-60%); (2) **more frequent forced wakes trade precision for recall** — the 30-min automatic condition drowned in false positives; (3) **agent-controlled cadence won overall** — letting the agent decide *when it needs a heartbeat* was the best precision/recall balance. This directly endorses "agent proposes its own next wake, platform clamps it."

Adjacent: [SentinelBench](https://arxiv.org/html/2606.05342) benchmarks long-running monitoring agents specifically; ["Anticipate and Learn"](https://arxiv.org/pdf/2605.25971) explores using idle time between wakes for precomputation.

### 1.3 Adaptive polling: backoff on quiet, tighten on activity

- **RT-IFTTT** ([RTSS 2017 paper](http://corelab.or.kr/Pubs/rtss17_rt-ifttt.pdf), [IEEE](https://ieeexplore.ieee.org/document/8277299/), [simulation code](https://github.com/corelab-src/rt-ifttt)): computes each sensor's polling interval from *how close current values are to any applet's trigger condition* plus the applet's deadline. Far from threshold → long interval; near threshold → tight interval. Result: 100-400 applets meeting user-defined real-time constraints with up to **64.12% fewer polls**. The transferable idea: polling frequency should be a function of **distance-to-trigger**, not a constant.
- **AIMD / backoff-style polling** ([adaptive polling patterns](https://medium.com/tech-pulse-by-collatzinc/modern-javascript-polling-adaptive-strategies-that-actually-work-part-1-9909f5946730), [smart-poll-loop pattern](https://lobehub.com/skills/dolodorsey-khg-skills-arsenal-smart-poll-loop), [reactive polling](https://dev.to/alex-nguyen-duy-anh/reactive-polling-efficient-data-monitoring-3ed)): effective interval = `base × multiplier`; multiply the interval up (×1.5-2) on each empty/quiet check to a cap, reset to base immediately on activity (multiplicative-increase-on-quiet, reset-on-hit — the polling analogue of AIMD). RSS fetchers do the same by learning each feed's publishing cadence ([intelligent feed fetcher](https://nikolajjsj.com/blog/building-an-intelligent-rss-feed-fetcher/)).
- **Webhook-primary, polling-fallback**: use push where available; keep a low-frequency reconciliation poll to catch missed deliveries. Stripe practice: retries webhooks up to 3 days, keeps events 30 days; a scheduled job pulls last-24h events and diffs against the local event log; idempotent handlers are mandatory because redelivery happens ([reliability patterns](https://dev.to/astraedus/stripe-webhook-reliability-patterns-every-saas-should-implement-2pg1), [Hookdeck guide](https://hookdeck.com/webhooks/platforms/guide-to-stripe-webhooks-features-and-best-practices)).

### 1.4 Watchdog/liveness in Postgres-backed job systems (numbers)

| System | Liveness signal | Cadence | Stale threshold | Orphan rescue |
|---|---|---|---|---|
| [Solid Queue](https://github.com/rails/solid_queue/blob/main/README.md) | `processes.last_heartbeat_at` row per process | `process_heartbeat_interval` = **60s** | `process_alive_threshold` = **5 min** | supervisor prunes dead processes; their claimed executions fail with `ProcessPrunedError` and are released ([failure/recovery internals](https://deepwiki.com/rails/solid_queue/7.3-process-failure-and-recovery); [issue #455](https://github.com/rails/solid_queue/issues/455) shows why threshold ≥ 3× interval) |
| [Oban](https://github.com/oban-bg/oban) | producer records as heartbeats | plugin-driven | — | [Lifeline plugin](https://oban.hexdocs.pm/2.23.0/Oban.Plugins.Lifeline.html) rescues `executing` jobs orphaned by node shutdown after `rescue_after` = **60 min** default |
| [pg-boss](https://pgboss.io/api/jobs) | `expireInSeconds` lease + optional worker heartbeat | heartbeat min **10s**, off by default | `expireInSeconds` default **15 min** (range 1s-24h) | job in `active` past expiry (or missing heartbeat) → failed/retried by monitor |
| [GoodJob](https://github.com/bensheldon/good_job) | session-scoped **advisory lock** + process heartbeat row | heartbeat, not job timeouts | process expiry | workers explicitly query for jobs whose process expired and unlock them; note their [discussion #831](https://github.com/bensheldon/good_job/discussions/831) on moving from advisory locks to `locked_at/locked_by` columns — advisory locks die with the connection (self-cleaning) but are hard to introspect |

Common shape: **lease + heartbeat + reaper**. Claim with a lease column (or advisory lock), refresh a heartbeat timestamp on a fixed cadence, and run a reaper that treats `now() - last_heartbeat > threshold` (threshold ≈ 3-5× cadence) as dead and re-enqueues the work.

### Recommendations for this platform (Area 1)

- **`wakeups` table** (agent-owned schedule): `id, agent_id, run_id, due_at, reason text, payload jsonb, min_interval, max_interval, created_by ('agent'|'system'|'user'), status ('pending'|'fired'|'cancelled'), fired_at`. Expose two registry tools to the agent: `schedule_wakeup(delay_or_at, reason)` and `cancel_wakeup(id)` — PM-Bench says optional/agent-controlled beats forced periodic; Claude Code says you must ship cancel + a done-guard from day one.
- **Clamp, don't trust**: platform clamps agent-proposed delays to `[60s, 24h]` (floor = the scheduler tick), enforces max N pending wakeups per agent (e.g. 5) and max wakeups/day per agent (e.g. 100 — budget guard against #58235-style loops).
- **Per-source adaptive polling state** on the watched-source rows: `base_interval_s int` (default 300), `current_interval_s int`, `backoff_multiplier real` (1.5-2.0), `max_interval_s int` (e.g. 3600), `last_activity_at`, `consecutive_quiet int`. On quiet check: `current = min(current × mult, max)`; on hit: `current = base`. If a source is bound to a near-due composite/timer, override to a tight interval (RT-IFTTT distance-to-trigger idea).
- **Liveness for the scheduler/runs**: keep the 60s advisory-locked tick; add `runs.last_heartbeat_at` updated every tick by the executing loop, and a reaper in the same tick that marks runs with `last_heartbeat_at < now() - 5 min` as `stalled` and either resumes (checkpoint) or fails them to the ledger. 60s/5min matches Solid Queue's proven defaults; advisory locks self-release on process death (GoodJob), which suits a single process.
- **Auto-heartbeat on tool failure** (Letta pattern): a failed tool call inside a run should schedule an immediate self-wake with the error in context rather than terminating the run.

## Area 2 — Composite events / lightweight CEP without a stream processor

### 2.1 The minimal operator core

CEP surveys and engines converge on a small set of composite operators: **sequence** (A then B), **conjunction** (A and B, any order, same window), **disjunction**, and **negation/absence** (A occurred, B did *not* occur within T) — the last being native to CEP and awkward everywhere else ([IBM CEP overview](https://www.ibm.com/think/topics/complex-event-processing), [lazy chain automata paper](https://arxiv.org/pdf/1612.05110), [CEP-to-simple-event-processing survey](https://arxiv.org/pdf/1702.08051)). Implementation is a per-rule **NFA/state machine instance keyed by a partition key** (user, entity), advanced by matching events, discarded on window expiry.

**Absence is a timer, not a query.** Every practical system implements "X did NOT happen by T" by *arming a timer when the expectation starts* and firing the action if the timer expires unmatched — not by continuously querying for non-existence:

- Esper/patent-style engines add explicit timer events: an "INCLUDE TIMER EVENTS"/`DURATION` clause arms a timer on the trigger event; timer expiry with no matching event = pattern match ([US9658903](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9658903), [variable-duration non-event matching US9098587](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9098587)).
- **Temporal** expresses it as durable code: `AwaitWithTimeout(condition, T)` blocks on a signal-driven condition and returns `ok=false` on timeout; signals are persisted in workflow history so nothing is lost across restarts ([Go SDK workflow package](https://pkg.go.dev/go.temporal.io/sdk/workflow), [signals+selectors tutorial](https://dev.to/lyonas/new-coding-tutorial-efficient-workflows-in-go-with-temporal-signals-selectors-14ne)). The reminder pattern is literally: `if !AwaitWithTimeout(replied, 3*day) { nudge() }`.
- **Home Assistant** gives end-users both halves: state triggers with `for:` (condition must *hold* for a duration — a debounced absence-of-change), and in scripts `wait_for_trigger` with `timeout:` + `continue_on_timeout:` for "if B doesn't arrive within T, do the fallback branch" ([script syntax docs](https://www.home-assistant.io/docs/scripts/), [community explainer](https://community.home-assistant.io/t/how-does-automation-wait-for-trigger-works/431864)). Note their bug history ([zero-timeout issue](https://github.com/home-assistant/core/issues/109586)) — treat `timeout: 0` as "no timeout," never "immediate."
- **SQL `MATCH_RECOGNIZE`** (Flink and standard SQL) expresses sequence-within-window declaratively: `PARTITION BY key ORDER BY ts PATTERN (A B) WITHIN INTERVAL '2' MINUTES`, `DEFINE` mapping predicates to variables; `WITHIN` is Flink's non-standard but essential addition that also bounds state ([Flink docs](https://nightlies.apache.org/flink/flink-docs-master/docs/dev/table/sql/queries/match_recognize/), [Confluent course](https://developer.confluent.io/courses/flink-sql/match-recognize/), [Ververica intro](https://www.ververica.com/blog/flink-sql-match_recognize)). You don't need Flink, but `PARTITION BY / PATTERN / WITHIN / DEFINE` is the right *shape* for a rule schema. Plain-Postgres equivalents: windowed self-join or `LAG()` over an events table for A-then-B; the absence case still wants an armed timer row, not a query.
- **Oban Pro workflows / iWF** show job-queue-native composition: DAG dependencies where a step runs only after upstreams complete — sequence without a stream processor ([Oban](https://github.com/oban-bg/oban), [iWF polling pattern](https://medium.com/@qlong/polling-design-pattern-in-iwf-d159d610215f)).

**Minimal core for this platform** = an `events` append-only table + a `pattern_instances` table (partial matches) + **absence timers materialized as scheduler due-times**. The 60s tick already gives a timer wheel; absence detection latency is bounded by the tick (≤60s late), which is fine for reminder-class work.

### 2.2 Safe chaining: preventing cascades and loops

Production automation systems use four complementary guards:

1. **Depth limits.** Salesforce hard-fails a transaction at **16 stacked trigger frames** ("maximum trigger depth exceeded") ([recursion guide](https://www.apexhours.com/how-to-avoid-recursion-in-trigger/), [architect decision guide](https://architect.salesforce.com/docs/architect/decision-guides/guide/record-triggered.html)). Requires propagating a depth counter with every derived event.
2. **Provenance/causation chains.** Carry `causation_id` (the event that directly caused this one) and `correlation_id` (root of the chain) on every derived event; a rule refuses to fire if its own rule-id already appears in the chain (**no-self-trigger**), and depth = chain length. Salesforce's cheaper variants — static already-processed ID sets per transaction, and "only fire if the watched field actually changed" ([codeLive on recursion](https://soobink.medium.com/codelive-preventing-trigger-recursion-2950a1a23de2)) — are the same idea scoped to one transaction.
3. **Rate-based detection.** Zapier/Make-style: count executions per trigger per window; ~**100 executions/60s** per trigger flagged as a probable loop — above legitimate traffic, below exponential blowup ([loop-melting postmortem](https://medium.com/@olowu.marydan/how-we-stopped-recursive-trigger-loops-from-melting-our-compute-fleet-498a4cb3e5d0)). Precise depth tracking vs. simple rate limiting is the documented industry split; rate limiting false-positives on bursts, depth tracking needs plumbing. Do both — they're cheap.
4. **Cooldowns/debounce.** Per-rule `cooldown_s`: after a rule fires for a given partition key, suppress re-fires for the window (Home Assistant users emulate this with `for:` + timers; alerting systems call it deduplication windows).

### Recommendations for this platform (Area 2)

- **`events` table**: `id bigserial, kind, source, partition_key, payload jsonb, occurred_at, ingested_at, causation_id bigint null, correlation_id bigint, depth smallint default 0`. Derived events copy `correlation_id`, set `causation_id`, and `depth = parent.depth + 1`.
- **`composite_rules`**: `id, kind ('sequence'|'conjunction'|'absence'), partition_key_expr, a_filter jsonb, b_filter jsonb, window_s int, cooldown_s int default 300, max_depth smallint default 4, enabled`. Rule vocabulary = exactly A-then-B-within-T, A-and-B-within-T, A-without-B-by-T. Resist a fuller pattern language until a real rule needs it.
- **`pattern_instances`**: `id, rule_id, partition_key, state ('armed'|'matched'|'expired'), a_event_id, deadline_at timestamptz, created_at`, unique `(rule_id, partition_key, state='armed')`. Sequence/conjunction: evaluate on event insert (same transaction or NOTIFY-driven). **Absence: on A, insert an armed instance with `deadline_at = occurred_at + window`; the 60s scheduler tick selects `armed AND deadline_at <= now()` under the existing advisory lock and emits the absence event.** This is the Temporal/Esper timer pattern with the tick as the timer wheel; ≤60s firing slop is acceptable for reminders.
- **Chaining guards (all four)**: reject derived events with `depth >= max_depth` (default 4, nowhere near Salesforce's 16 — ambient chains should be short); refuse to fire a rule whose id already appears in the correlation chain (walk `causation_id`, or cache `rule_path text[]` on the event); per-rule counter with kill-switch at **50 fires/rule/hour** (auto-disable + ledger entry + HITL notification); per-`(rule, partition_key)` cooldown default **300s**.
- Log every rule firing to the runs ledger with `correlation_id` so a cascade is reconstructable after the fact.

## Area 3 — Presence/attention detection and delivery timing

### 3.1 Detecting presence and the "user returned" moment

Four signal layers, cheapest first ([presence detection guide](https://portalzine.de/the-ultimate-guide-to-presence-detection-in-javascript-what-works-and-why/), [Hoverify how-to](https://tryhoverify.com/blog/how-to-add-user-presence-to-web-apps/)):

- **Page Visibility API** — `visibilitychange` fires on tab switch/minimize; `document.visibilityState` tells you visible vs hidden. Free, universal, but "visible" ≠ "attending."
- **Activity events** — throttled listeners on mouse/key/scroll/touch maintain `last_activity_at`. This is what Slack's presence actually is: **~10 min without input → auto-away on desktop** (hardcoded server-side, not configurable); mobile flips to away **within 1-2 min** of backgrounding; multi-device presence is OR-ed across devices ([Slack idle timeout](https://idlepilot.com/glossary/slack-idle-timeout/), [auto-away mechanics](https://idlepilot.com/glossary/slack-auto-away/), [presence guide](https://idlepilot.com/slack-presence-guide/)).
- **Client heartbeat / WebSocket liveness** — ping every **30-45s** (≈75% of typical proxy idle timeouts); terminate connections that miss a pong; **send an immediate heartbeat on `visibilitychange` → visible** and treat missed pong as reconnect-now ([WebSocket.org heartbeat guide](https://websocket.org/guides/heartbeat/), [implementation how-to](https://oneuptime.com/blog/post/2026-01-27-websocket-heartbeat/view)). A common presence recipe: heartbeat every 30s, mark idle after **5 min** without one. GA4 uses **30 min** inactivity as session end ([GA4 sessions](https://support.google.com/analytics/answer/12798876?hl=en)) — a sensible "long absence" boundary.
- **Idle Detection API** — `IdleDetector` reports user `active/idle` and screen `locked/unlocked` **system-wide**, beyond the page (explicitly motivated by "if I showed a notification, would it be perceived?"); requires a permission grant, threshold ≥ 60s, Chromium-only ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Idle_Detection_API), [WICG explainer](https://github.com/wicg/idle-detection/blob/main/README.md)). Treat as progressive enhancement.

**"User returned"** = edge detection: transition from (hidden or idle-past-threshold) to (visible AND recent input). Concretely: `visibilitychange→visible` or first input event after `now() - last_activity_at > idle_threshold`. The WebSocket guide's "immediate heartbeat on foreground" is exactly this edge made server-visible.

### 3.2 Flushing pending output when the user returns

- **Slack recaps / catch-up**: a **morning digest** of unread activity in opted-in channels; if you were away multiple days, one recap covers the whole gap; Slack seeds the channel list by recommending channels you *read but rarely participate in* — i.e., qualification = (unread) ∧ (user demonstrably cares) ∧ (not important enough to interrupt) ([Slack AI features guide](https://slack.com/help/articles/25076892548883-Guide-to-AI-features-in-Slack), [Slack AI announcement](https://slack.com/blog/news/slack-ai-has-arrived)). Delivery is anchored to a natural boundary (morning), not literally the return edge.
- **Gmail nudges**: ML picks *which* threads resurface (sender relationship, your habits, thread context) after **2-5 days** of inactivity (observed "3/4/5 days ago" nudges); user cannot tune timing; deliberately low-volume and it "quietly misses some" — precision over recall ([9to5Google launch coverage](https://9to5google.com/2018/05/14/new-gmail-web-nudge-ai-reminders/), [nudges guide](https://mailmeteor.com/blog/gmail-nudges)). Lesson: absence-triggered reminders should be conservative and few, because each false nudge costs trust.
- Agent-platform practice converges on **digest windows aligned to workday rhythm** (start of day, post-lunch, end of day) for low-urgency agent output, reserving synchronous channels for genuine emergencies ([agent notification triage write-up](https://zylos.ai/zh/research/2026-04-23-agent-notification-intelligence-smart-alerting-triage/), [Google Labs situationally-aware agents](https://labs.google/code/experiments/situationally-aware-agents)).

### 3.3 Published heuristics for interrupt-worthiness

- **Horvitz, bounded deferral** ([MSR-TR-2005-87](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2005-87.pdf), [studies page](https://erichorvitz.com/bdef_studies.htm)): hold a notification while the user is busy, but only up to a **priority-dependent maximum bound**, then deliver regardless; deliver early if the user becomes free. Empirical companion work found **medium-urgency email tolerates ~3 min deferral, low-urgency ~4 min** with negligible awareness cost. The [Attention-Sensitive Alerting](https://arxiv.org/pdf/1301.6707) line frames it as expected-value: interrupt iff `cost_of_delayed_awareness > cost_of_interruption(user_state)`.
- **Breakpoint delivery**: Attelia detected task breakpoints on-device and delivering at breakpoints cut frustration **~28%** vs random timing ([attention-aware adaptive notification](https://www.researchgate.net/publication/284018527_Towards_attention-aware_adaptive_notification_on_smart_phones)); a social-context variant defers until breakpoints like a lull in conversation or the user being alone ([breakpoint-based system](https://www.researchgate.net/publication/313739061_Don't_Bother_Me_I'm_Socializing_A_Breakpoint-Based_Smartphone_Notification_System)). Survey of the whole field: [Intelligent Notification Systems](https://arxiv.org/pdf/1711.10171).
- **Tiering in practice**: 3-4 tiers — interrupt (page/push now, any state), notify (deliver on next attention edge, bounded), digest (batch to scheduled windows), silent (ledger only) — with **silence treated as an explicit, logged decision**, since over-notifying is the canonical proactive-agent failure ([Google Labs](https://labs.google/code/experiments/situationally-aware-agents), [triage write-up](https://zylos.ai/zh/research/2026-04-23-agent-notification-intelligence-smart-alerting-triage/)). PM-Bench's 489 false positives from over-eager heartbeats is the same precision lesson on the sensing side.

### Recommendations for this platform (Area 3)

- **`user_presence`**: `user_id, state ('active'|'idle'|'away'|'offline'), last_activity_at, last_heartbeat_at, visible bool, session_id, updated_at`. Client: throttled activity listeners + `visibilitychange` handler + heartbeat over the existing WebSocket every **30s**, immediate beat on foreground. Server: `active` = beat < 60s ago ∧ visible ∧ input < **5 min**; `idle` = beat fresh but no input 5-30 min; `away` = no beat 2 min or hidden; `offline` = no beat > **30 min** (GA4 boundary). Emit a `user_returned` event on the away/idle→active edge — it enters the Area 2 event stream, so composite rules and flushes can key off it.
- **`pending_deliveries` (outbox)**: `id, user_id, run_id, tier smallint (0=interrupt,1=notify,2=digest,3=silent), created_at, deliver_no_later_than timestamptz, delivered_at, delivery_channel, superseded_by bigint null, payload jsonb`. Tier semantics: **0** = push immediately regardless of presence (reserve for HITL gates blocking a run and hard failures); **1** = flush on next `user_returned` edge, with bounded deferral `deliver_no_later_than = created_at + 30 min` (Horvitz: bound by priority; his 3-4 min was for desk workers mid-task — ambient-agent "notify" tolerates more) enforced by the 60s tick; **2** = digest, flushed on `user_returned` if the batch is nonempty and stale > 1h, else at fixed windows (09:00 / 17:00 local); **3** = ledger-visible only. One digest covers the whole absence, however long (Slack recap behavior).
- **Flush-on-return rule**: on `user_returned`, deliver all tier-1 items and, if the user was away > **1 h**, a single collapsed "while you were away" digest of tier-2 items; if away < 5 min, deliver tier-1 only (don't recap micro-absences). Use `superseded_by` so stale items (e.g. "build running" superseded by "build done") collapse instead of stacking.
- **Anti-spam guards**: per-user cap on tier-0 (e.g. 3/day before requiring HITL escalation config), and log tier-3 silences to the runs ledger with a reason — silence as an explicit decision, auditable later.
- Default tier assignment prompt-side: agents must *justify* tier ≤ 1 (interrupt/notify) in the run record; default is digest. Gmail's design point — conservative, misses some, keeps trust — is the right bias for an ambient agent.
