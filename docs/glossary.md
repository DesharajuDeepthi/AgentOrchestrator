# Glossary

The decoder ring for the Concierge Agent's invented and loaded vocabulary. Every term below is used in the repo; "where it lives" points at the defining spec section and/or code.

| Term | Definition | Where it lives |
|---|---|---|
| **A2UI** | The declarative answer-UI protocol (v0.9). The backend translates a model-generated component tree into A2UI `createSurface`/`updateComponents` messages; the frontend renders them with the official `@a2ui/react` renderer. Payloads are data, never markup. | spec §7.1; `backend/app/orchestrator/answer_ui.py`; `frontend/src/components/AnswerUiView.tsx` |
| **activity ticker** | The one-line live readout in Chat showing the steps currently executing (names only, no payloads), driven by `activity` SSE events. | spec §8.5; `frontend/src/pages/ChatPage.tsx` |
| **agentic mode** | One of the two orchestrator modes: a single `create_agent` concierge loop with todo-driven emergent planning; capabilities arrive as tools via the registry middlewares. Contrast *graph mode*. | spec §7.2; `backend/app/orchestrator/agentic_mode.py` |
| **aggregator** | The final LLM call that merges worker outputs into the one chat answer (and streams the `token` events). Has its own model/params setting (`aggregator_model`). | spec §7.2; `backend/app/prompts/aggregator.md`; Settings → Models |
| **answer UI / answer panel** | The optional model-generated structured view of an answer (cards, tables, stats, charts), persisted on `runs.answer_ui` and rendered primary or collapsed per the artifact's own `presentation` (frozen at run time). Failure-safe: the markdown text is always the source of truth, and a run without an artifact shows no structured toggle at all. | spec §7.1, §8.5; `answer_ui.py`; `frontend/src/components/AnswerPanel.tsx` |
| **bypass mode** | The default registry-cache mode: no cache state at all, every read is a direct Postgres query. The rollback lever for the cache layer. | spec §7.3; `backend/app/registry_cache.py` |
| **callsign** | The per-run sequential phonetic name given to an ephemeral worker — `worker-alpha`, `worker-bravo`, … shown with its skill composition, e.g. `worker-alpha (web-research+file-ops)`, so parallel workers stay distinguishable in rails, ticker, and trace. | spec §7.1 rung 4; `backend/app/orchestrator/context.py` (`WORKER_CALLSIGNS`) |
| **capability** | Anything a plan entry can resolve to: a direct tool, a direct skill, a sub agent, or a `spin_worker` request. The unit the resolution ladder operates on. | spec §7.1; `backend/app/orchestrator/ladder.py` |
| **catalog** | The compact registry summaries injected into orchestrator prompts (sub agent cards + exposed tools/skills). Ranked/truncated by retrieval when large; widened by *full-catalog* mode. | spec §7.1, §7.4; `backend/app/orchestrator/middleware.py`, `retrieval.py` |
| **checkpointer** | The LangGraph Postgres checkpointer keyed by run — what makes HITL pause/resume (and resume-after-restart) possible. | spec §6; `backend/app/db.py` |
| **conversation** | The multi-turn chat container; every run belongs to one, and the planner receives the full conversation history as context. | spec §3.6; `frontend/src/pages/ChatPage.tsx` |
| **covers_skill_ids** | A native sub agent's declaration of which registry skills it can service — what rung 2 of the ladder matches on. | spec §3.4; `backend/app/orchestrator/ladder.py` |
| **direct exposure** | The `direct_exposure` flag on a tool or skill: when true, the orchestrator may use it itself (rung 1) without a sub agent. Shown as the `direct` badge; toggled in the Tools/Skills drawers. | spec §3.2, §3.3; `frontend/src/pages/ToolsPage.tsx` |
| **dispatch rail** | The per-capability card in Chat's live run view (one per `dispatch_start` event), under which the sub agent's own skill runs, tool calls, and gate card nest. | spec §8.5; `ChatPage.tsx` (`DispatchCard`) |
| **dispatch wave** | A group of plan entries with no unmet dependencies that dispatch in parallel; the plan card renders entries grouped as "wave 1", "wave 2", … with a `∥ parallel` marker. | spec §7.1; `ChatPage.tsx` (`PlanCard`) |
| **dynamic worker / ephemeral worker** | The rung-4 fallback: a worker the factory builds on the fly over one or more **`direct_exposure=true`** skills, never persisted to a registry, traced with `kind='dynamic'` under a callsign, discarded after the run. A non-exposed skill is rejected — it is reachable only through a sub agent that owns it or through the full-catalog fallback, which runs it inline in the open. | spec §7.1 rung 4; `ladder.py` |
| **effort** | The normalized reasoning knob in `ModelParams` (`none/low/medium/high`); each provider adapter maps it to its native control (thinking budget, reasoning effort, thinking config). Part of the trace label set. | spec §2.1; `backend/app/llm/port.py` |
| **error edge** | A workflow edge with `on: "error"`: when its node fails, execution routes through it with the error text in state instead of failing the run. At most one per node. | spec §3.5; `backend/app/factory/dag.py` |
| **formatter** | The explicit presentation role (spec §7.1): a per-run model call that transforms the canonical answer into the structured A2UI artifact with content parity as the goal. Off = no call, no artifact — raw renders directly with no toggle. Has its own model/params/presentation settings. | spec §7.1; `backend/app/orchestrator/answer_ui.py`; Settings → Formatter |
| **coverage** | Deterministic content-retention percent stamped on each formatter artifact: the fraction of the raw answer's numbers/URLs/code spans present in the structured view. A badge and instrument, never a render gate. | spec §7.1; `answer_ui.compute_coverage` |
| **form gate** | An HITL node carrying a `questions` array (`approve`/`choice`/`text`). Chat renders all questions on one card with a single Submit; answers land on the hitl step and in worker state. Malformed specs degrade to the plain approve/deny card. | spec §3.5; `ChatPage.tsx` (`HitlCard`) |
| **full-catalog fallback** | The self-service backup when semantic routing fails: the orchestrator handles the query itself with ALL active tools and skills callable, exposure flags ignored. Traced as route rung `fallback`; rendered as an amber banner in Chat. | spec §7.0; `middleware.py` (`FallbackLoopContext`) |
| **generation (cache)** | The per-registry counter in the registry cache, bumped on every invalidation — the `gen N` in cache status lines; watching it move proves event invalidation. | spec §7.3; `registry_cache.py` |
| **graph mode** | The default orchestrator mode: a hand-built StateGraph running `plan → resolve → dispatch (parallel) → aggregate` with an explicit validated plan. Contrast *agentic mode*. | spec §7.1; `backend/app/orchestrator/graph_mode.py` |
| **HITL / gate** | Human-in-the-loop: a workflow node that pauses the run (`paused_hitl`) at a checkpoint until a human approves, denies, or submits form answers — via the chat card, the Runs drawer, or the Settings HITL queue. | spec §3.5, §7.2; `POST /runs/{id}/hitl` |
| **ladder / rung** | The deterministic capability-resolution order: rung 1 direct tool/skill → rung 2 native sub agent → rung 3 custom sub agent → rung 4 ephemeral worker (plus `fallback` outside the ladder). Every decision is logged as a `route` step naming its rung. | spec §7.1; `ladder.py` |
| **listChanged** | The MCP tool-list-changed notification the connection manager subscribes to; on receipt it re-runs `tools/list` and reconciles the tool registry automatically. | spec §5; `backend/app/mcp/manager.py` |
| **MCP** | Model Context Protocol — the standard by which external tool servers (stdio subprocesses or HTTP endpoints) expose tools the system ingests. | spec §5; `backend/app/mcp/` |
| **middleware projection** | The three custom registry middlewares (Tools/Skills/SubAgents) that project live Postgres registry state into every `create_agent` loop, fresh per model call — the only path capabilities reach a loop. | spec §7.0; `backend/app/orchestrator/middleware.py` |
| **kind (mcp / native / custom)** | The per-tier discriminator on registry records: tools are `mcp` or `native`; skills and sub agents are `native` or `custom`; sub-agent-tier trace labels add `dynamic` for ephemeral workers. Rendered as the kind badge. Not to be confused with *source*. | spec §3; `frontend/src/components/ui.tsx` (`KindBadge`) |
| **overlap guard** | The advisory LLM-as-judge duplicate check run before a skill/sub-agent save; at ≥70% overlap the UI offers Save anyway / Cancel. Fails open — never blocks a save on judge trouble. Tools are exempt. | spec §4; `backend/app/overlap.py`; `frontend/src/components/OverlapDialog.tsx` |
| **pinned ids** | Ids exempt from retrieval ranking: entities referenced by the current plan or already used in the run always survive catalog truncation. | spec §7.4; `retrieval.py`, `recorder.py` |
| **planner** | The graph-mode structured-output LLM call that turns the user message (plus conversation history) into a validated plan of capability entries with dependencies. Has its own model setting; invalid output gets one repair retry. | spec §7.1; `backend/app/orchestrator/planner.py`; `prompts/planner.md` |
| **progressive disclosure** | The token-economy principle: the orchestrator sees compact summaries (cards, exposed capabilities) rather than full definitions; detail is disclosed only when a capability is actually invoked. Retrieval (§7.4) extends it to ranked top-K catalogs. | spec §7.1, §7.4 |
| **registry** | One of the Postgres-backed capability tables (mcp_servers, tools, skills, sub_agents) — single source of truth, two write paths (static seed, dynamic UI), one read path. | spec §1, §4 |
| **registry cache** | The `RegistryCache` facade all registry/settings reads in the run path go through, with swappable backends (`bypass`/`memory`/`redis`) and event-driven invalidation — never TTLs. | spec §7.3; `backend/app/registry_cache.py` |
| **resolution** | The act of mapping a plan entry's capability to something executable via the ladder; recorded as a `route` step with the chosen rung and resolved entity. | spec §7.1; `ladder.py` (`Resolution`) |
| **RRF** | Reciprocal-rank fusion — how retrieval merges the BM25 lexical ranking with the embedding-cosine ranking into one top-K order. | spec §7.4; `retrieval.py` (`rrf_fuse`) |
| **run / step / event** | The trace hierarchy: a *run* is one chat message's execution (`runs` row); a *step* is one recorded unit inside it (`run_steps` row, typed `plan/route/skill/hitl/tool_call/aggregate`, nested via `parent_step_id`); *events* are the SSE messages (`plan`, `route`, `activity`, `token`, `hitl_request`, …) that stream the run live, plus the structlog events mirroring each step. | spec §3.6, §7.1; `recorder.py` |
| **skill document** | The one authoring format for skills: YAML frontmatter (name, description, persona, tools, direct_exposure) + markdown instructions body. Native skills are `.skill.md` files; custom skills are the same shape authored in the UI. | spec §3.3; `backend/app/skilldoc.py`; `native/skills/` |
| **snapshot** | The resolved configuration (personas, workflows, models, tool definitions) frozen onto the run at dispatch time, so later registry edits never rewrite trace history. Shown in the Runs drawer. | spec §3.6; `runs.snapshot` |
| **source (static / dynamic)** | Where a registry record came from: `static` = seeded/code-registered at startup, `dynamic` = created through the UI at runtime. Orthogonal to *kind*; rendered as the source badge. Static records reject definition writes — only status/exposure toggle. | spec §3, §4; `ui.tsx` (`SourceBadge`) |
| **spin_worker** | The agentic-mode tool (and plan capability type) that requests a rung-4 ephemeral worker over explicit skill ids — a strict UUID-pinned contract over exposed skills only, never subject to retrieval. | spec §7.2, §14.7; `middleware.py`, `ladder.py` |
| **structured summary** | The operator-facing name for the answer-UI panel: the "show structured summary" toggle under a chat answer that expands the A2UI cards and charts. | spec §8.5; `AnswerPanel.tsx` |
| **sub agent** | The top capability tier: persona + workflow DAG over skills (custom, factory-compiled) or a hand-written registered graph (native). Dispatched by the orchestrator, never nested inside tools. | spec §3.4; `backend/app/factory/worker.py` |
| **thinking** | Streamed model reasoning (`thinking` SSE events), rendered as a dimmed collapsible block in Chat, never mixed into the answer prose. Controlled by the model's *effort* params. | spec §7.1; `ChatPage.tsx` |
| **tier** | The trace label naming the layer a step belongs to: `tool`, `skill`, `sub_agent`, or `orchestrator`. | spec §10; `backend/app/obs.py` |
| **tool_key** | A tool's human-facing identifier — `{server}.{tool_name}` for MCP tools, the registration name for native ones. Renameable; internal bindings always use the immutable id. | spec §3.2 |
| **top-K retrieval** | The opt-in progressive-disclosure ranker: above a threshold, orchestrator catalogs are ranked (BM25 + optional embeddings, RRF-fused) and truncated to the task's K most relevant records, with pinned ids kept and a "showing N of M" footer. | spec §7.4; `retrieval.py`; Settings → Retrieval |
| **use_full_catalog** | The agentic-mode escalation tool that flips the registry middlewares into full-catalog mode mid-loop (logged as a `fallback` route); also the footer hint retrieval leaves on truncated catalogs. | spec §7.0, §7.4; `middleware.py` |
| **worker factory** | `build_worker(record) → CompiledStateGraph`: compiles a workflow DAG into a LangGraph graph (`create_agent` at skill leaves, explicit StateGraph shell), validates at save time, caches by `(id, updated_at)`. | spec §6; `backend/app/factory/worker.py` |
