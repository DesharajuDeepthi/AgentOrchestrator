## Stage 25 — Memory: highlights and honest findings

- **The whole spec §16 lifecycle worked exactly as documented on the first real pass.** A chat message ("My favorite color is teal... from now on, always answer in bullet points.") produced two extracted memories after the run: the preference landed `active` immediately, the instruction landed `quarantined` — precisely the admission-gate rule in `app/memory/store.py` ("extracted/inferred instruction-kind memories always land quarantined").
- **Real citation-quality recall.** A brand-new conversation asking "What is my favorite color?" (never restated) answered: *"According to your saved preference (memory 032af959), your favorite color is deep teal."* — the model cited the memory ID unprompted, in the exact style the extraction prompt describes machine writes using internally. This is genuine recall injection working end-to-end, not a scripted demo.
- **Finding (not a bug, worth documenting): passive recall doesn't move `access_count`/`last_accessed_at`.** After the recall run above, the memory detail drawer still showed `accessed 0×`. Reading the injection code, those fields appear to only advance through the explicit citation-feedback loop (M18), not plain recall/injection. Anyone building on top of "last accessed" as a proxy for "was used in context" should know it currently isn't.
- **"Communities" (temporal-KG, M31) has no dedicated UI.** `memory_community_budget_tokens` and the community-summary machinery (`app/memory/communities.py`) are real and wired into recall injection, but there's no Memory-page view for them — verified structurally (entity/relation-kind rows, injection code path) rather than through a page, since none exists.

## Stage 26 — Ambient: highlights and honest findings

- **No in-UI Settings toggle for `ambient_enabled` exists.** The Ambient nav item and page are fully built and gated correctly on the setting (`App.tsx`'s `NavItems` hides `/ambient` until it's true), but there is no control anywhere in `SettingsPage.tsx` to flip it — it can only be set via `PATCH /api/v1/settings` directly. Memory has the same shape of gap covered (its layers *do* have Settings toggles), so this looks like an oversight specific to ambient rather than a deliberate "admin-only" design choice. Worth a follow-up ticket.
- **A genuine external fire, over real HTTP, end to end.** A routine was created through the typed trigger builder (webhook trigger + a `contains` filter), issued a fire token through the UI, then fired exactly the way an outside webhook integration would: `POST /routines/{id}/fire` with `Authorization: Bearer <token>` and an untrusted JSON body. The fire produced a ledgered decision, a real run, an LLM-authored remediation proposal, and (once routed past the digest window) a delivery sent to both configured external channels.
- **Finding worth documenting: tier-1 webhook filters match against the event's *inner* `payload` object, not its top-level fields.** The fire body is `{"text": ..., "payload": {...}}`; `app/ambient/decide.py`'s `match_filters` call passes only `event.payload["payload"]` to the matcher. A filter on `field: "text"` matching against the *outer* `text` key — the natural first guess when reading the trigger builder's own field placeholder text ("field (e.g. `sev` or `payload.repo`)") — silently holds every fire with "webhook trigger filters did not match". This is exactly the mistake this campaign made on the first attempt (captured honestly in the stage's ledger as a real `held` row, left in place rather than deleted, right next to the corrected `fired` rows). Anyone authoring webhook-trigger filters needs to target fields *inside* the fire's `payload` object.
- **Digest delivery is quiet-hours-gated, including catch-up flushes.** With the default `ambient_quiet_hours: ["22:00", "07:00"]`, a digest that becomes due at, say, 01:00 UTC will not flush — "even a catch-up digest waits them out" per the code's own comment. This campaign ran at 01:00 UTC and had to temporarily narrow the quiet-hours window to get a live delivery; the setting was restored to its default afterward. Not a bug, but a real operational trap for anyone testing or demoing ambient delivery outside business hours without noticing quiet hours are active.
- **A genuine emergent behavior, unprompted:** the second (`db-02`) alert's LLM-authored remediation proposal referenced the first (`db-01`) alert as a prior episode — *"This mirrors the earlier `db-01` alert [episode 788831d6]..."* — via episodic memory recall, without any instruction in the routine prompt to do so. Memory and ambient composing correctly, live.
- **Auth/tenancy (M34) two-user pass deferred.** A live two-identity demonstration requires flipping `AUTH_ENABLED` (an env var, not a runtime setting) and restarting the backend container, plus seeding a second user — a real risk to the shared live stack this late in a long campaign, for a feature outside the explicit ask (memory + ambient). M34's original acceptance evidence (`docs/acceptance/auth_m34/`) already covers this feature live; this campaign did not re-prove it and says so rather than skipping silently.
- **Evals page (§15)** was captured once in its clean empty state for completeness. It's outside the requested memory/ambient scope and wasn't otherwise exercised.

## Cross-cutting findings carried over from the base-parity replay (stages 00–24)

These were caught and either fixed in code or worked around honestly during the replay; none are new to this campaign, but are recorded here since this is the closing report for the whole effort:

- **HashRouter quirk**: `page.goto()` to the same hash is a browser no-op — a left-open Drawer must be closed explicitly (✕) before the next action, or it intercepts clicks.
- **Real-LLM latency is highly variable and was consistently underestimated on the first attempt at every stage** — from 15s (simple replies) up to ~25 minutes (agentic + high-effort research runs). Every stage's wait budgets were widened based on *observed* failures, never preemptively over-padded.
- **Provider-specific quirks, both genuine platform behavior**: `qwen/qwen3.8-max` via OpenRouter rejects `effort=none` ("reasoning is mandatory for this endpoint"); `openai:gpt-5.6-terra` rejects `reasoning_effort` combined with tool-calling on `/v1/chat/completions` (confirmed systematic across two independent attempts, worked around with `gpt-4o` for that sub-test, documented rather than hidden).
- **OpenRouter's new-account rate limit (20 req/min)** was hit during the heaviest-traffic stages; no code fix applicable, just pacing awareness.
- **`IntSetting` silently rejects values below 1** — client-side guard in `SettingsPage.tsx`, worth knowing when scripting settings changes through the UI rather than the API.
- **The scrollable region is `<main>`, not `window`** — `window.scrollTo` is a no-op on this layout; `document.querySelector('main').scrollTo(...)` is required for any script that needs to reset scroll position before a screenshot.
