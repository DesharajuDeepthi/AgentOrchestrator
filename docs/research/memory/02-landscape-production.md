## 1. Letta / MemGPT

**(a) Data model.** The classic MemGPT design is a three-tier hierarchy: **core memory** = labeled, size-limited string blocks pinned into the system prompt (conventionally `human` and `persona`, plus custom blocks for task/project state); **recall memory** = the full message history on disk, searchable; **archival memory** = an embedding-indexed passage store for unlimited facts ([letta.com/blog/memory-blocks](https://www.letta.com/blog/memory-blocks/), [docs.letta.com/memory](https://docs.letta.com/memory)). A block has four fields: `label`, `value`, size `limit`, and an optional `description` telling the agent how to use it; blocks are DB rows with stable IDs and can be **attached to multiple agents simultaneously** (shared memory). In 2026 Letta pivoted to **MemFS**: a git-backed memory *filesystem* per agent, files as Markdown with YAML frontmatter; `system/persona.md` and `system/human.md` are pinned into the prompt every turn, everything else (e.g. `reference/`, `skills/`) stays out of context until read; the file tree itself is always visible as a navigation signpost ([docs.letta.com/concepts/memfs](https://docs.letta.com/concepts/memfs)). Block size-limit validation was removed from the git sync path in the 2026-03-31 release — blocks now grow freely ([docs.letta.com/letta-agent/changelog](https://docs.letta.com/letta-agent/changelog)).

**(b) Write path.** The agent itself writes memory via tools mid-conversation: `memory_insert`, `memory_replace`, `memory_rethink` (rewrite a whole block) for core memory; `archival_memory_insert` for passages; developers write via API (`client.agents.passages.create()`, blocks CRUD) ([docs.letta.com/guides/agents/archival-memory](https://docs.letta.com/guides/agents/archival-memory)). In MemFS, edits are git commits; subagents use **git worktrees** to update memory concurrently without blocking the main agent.

**(c) Read path.** Core blocks are always in-context (compiled into the system prompt each turn). Archival is pulled on demand via `archival_memory_search` (semantic + tag + timestamp filters); history via `conversation_search`. Nothing is auto-injected from archival — retrieval is agent-initiated.

**(d) Consolidation & forgetting.** Two mechanisms. (1) **Memory pressure/eviction** (from-training, per the MemGPT paper arXiv:2310.08560): when the context queue approaches capacity the runtime emits a pressure warning, evicts oldest messages to recall storage, and replaces them with a recursive summary — eviction is lossy in-context but lossless on disk. (2) **Sleep-time agents** (arXiv:2504.13171, from-training for the paper ID): background subagents that run while the main agent is idle, re-reading recent transcripts and rewriting shared memory blocks with distilled "learned context." Current Letta calls this **dreaming**: background subagents triggered after N agent steps or on context compaction, with an optional "agent reviews before applying" second-pass gate ([docs.letta.com/guides/agents/architectures/sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime)).

**(e) API surface.** Tools: `memory_insert`, `memory_replace`, `memory_rethink`, `archival_memory_insert`, `archival_memory_search`, `conversation_search`; SDK: `client.agents.passages.create()/search()`, blocks CRUD + attach; `enable_sleeptime=True` on agent creation (from-training for the exact flag; the docs page confirms the feature but the excerpt retrieved documents CLI/app config).

**(f) Steal for Postgres+LangGraph.** The block abstraction maps 1:1 onto rows: `memory_blocks(id, label, value, char_limit, description, agent_scope)` rendered into the system prompt by middleware; "shared block" = FK from multiple agents. Sleep-time/dreaming is precisely the ambient mode: an idle-time asyncio task that rewrites blocks from the runs ledger, with the existing HITL gate as the "review before applying" step.

**(g) Weaknesses.** Self-editing memory burns tool-calls in the hot path and small models mangle `str_replace`-style edits; two divergent architectures (blocks vs MemFS) make the docs a moving target; archival is a flat vector store (no relations, no temporal invalidation); dreaming multiplies token spend.

## 2. Mem0 (and Mem0-graph)

**(a) Data model.** Atomic natural-language fact strings ("Customer prefers email"), each with id, embedding, scope keys (`user_id`, `agent_id`, `run_id`, `app_id`), metadata, optional `expiration_date`, plus a **history table** logging every mutation for audit ([docs.mem0.ai](https://docs.mem0.ai/core-concepts/memory-operations)). The graph variant (Mem0^g, per the paper arXiv:2504.19413, from-training for internals) additionally stores entity nodes and relationship-triplet edges in Neo4j/Memgraph.

**(b) Write path.** `add(messages, user_id=...)` with `infer=True` (default) runs a two-phase LLM pipeline (per the paper): **extraction** — an LLM reads the newest message pair plus a rolling conversation summary and recent messages, emitting candidate facts; **update/reconciliation** — for each candidate, top-k similar existing memories are retrieved and an LLM tool-call picks **ADD / UPDATE / DELETE / NOOP** against them. Note a live-docs discrepancy worth tracking: Mem0's current platform docs describe the pipeline as "additive — new memories are added without overwriting or deleting existing memories," with relevance resolved at retrieval time ([docs.mem0.ai/core-concepts/memory-operations](https://docs.mem0.ai/core-concepts/memory-operations)), i.e. the hosted product appears to have softened destructive reconciliation; the OSS `Memory`/`AsyncMemory` classes retain the classic operations. `infer=False` stores raw messages verbatim. Graph variant: entity extraction → triplets → conflict detection marks superseded edges obsolete rather than deleting (paper, from-training).

**(c) Read path.** `search(query, user_id=..., filters=...)` — embedding search + filters, returns scored fact strings the caller splices into the prompt; `get_all()` for full dumps. Mem0 is retrieval-only; injection is the caller's job.

**(d) Consolidation & forgetting.** Consolidation *is* the update phase (UPDATE merges, DELETE removes contradicted facts); `expiration_date` gives TTL; `history()` preserves an audit trail of ADD/UPDATE/DELETE events ([docs.mem0.ai/open-source/features/async-memory](https://docs.mem0.ai/open-source/features/async-memory)).

**(e) API surface.** `Memory`/`AsyncMemory`: `add`, `search`, `get`, `get_all`, `update`, `delete`, `delete_all`, `history`, `reset`; configured via `MemoryConfig` (vector store, LLM, embedder, graph store).

**(f) Steal.** The **ADD/UPDATE/DELETE/NOOP reconciliation loop** as a single structured-output LLM call is the cheapest credible dedup/contradiction mechanism and drops cleanly onto a Postgres table; the per-memory **history table** matches the runs-ledger culture — every memory mutation should be a ledger row.

**(g) Weaknesses / the LOCOMO fight.** Mem0's paper claimed SOTA on LOCOMO (Mem0 J≈66.9, graph ≈68.4, reporting Zep at 65.99 — from-training for exact figures; Mem0's current research page advertises later, higher self-reported numbers: LOCOMO 92.5, LongMemEval 94.4 at ~6.9k tokens/retrieval, [mem0.ai/research](https://mem0.ai/research)). Zep's 2025-05-06 rebuttal ("Lies, Damn Lies, & Statistics") alleged Mem0 misconfigured Zep — both speakers assigned the `user` role, timestamps appended to text instead of `created_at`, sequential searches inflating latency — and reported a corrected Zep J=75.14% vs 0.632s p95 search ([blog.getzep.com](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). Mem0 counter-claimed Zep's rerun included adversarial question categories the benchmark spec excludes, recomputing Zep at 58.44% ([survey of the dispute](https://agentmarketcap.ai/blog/2026/04/11/agent-memory-architecture-production-2026)). Zep also attacked LOCOMO itself: conversations of only ~16k–26k tokens, missing ground truth in category 5, speaker-attribution errors, no knowledge-update questions. Net lesson: treat all vendor memory benchmarks as marketing; LOCOMO is too small to stress real systems. Other criticisms: fact atomization loses discourse context; extraction LLM calls add cost/latency to every turn unless run async; hosted-vs-OSS behavior drift.

## 3. Zep / Graphiti

**(a) Data model.** Graphiti (OSS engine under Zep) is a temporal knowledge graph with three node tiers: **episode nodes** (raw ingested data: `text`, `message`, or `json`), **entity nodes** (extracted, deduplicated), and **community nodes** (clusters built by label propagation summarizing related entities); semantic **edges** carry a natural-language `fact` plus **bi-temporal fields** — `valid_at`/`invalid_at` (when the fact was true in the world) and `created_at`/`expired_at` (when the system learned/superseded it) ([Zep paper arXiv:2501.13956](https://arxiv.org/pdf/2501.13956), [github.com/getzep/graphiti](https://github.com/getzep/graphiti)). Episodic edges link facts back to source episodes bidirectionally, giving citation/provenance. Custom entity and edge ontologies are declared as Pydantic models.

**(b) Write path.** `add_episode()` (or `add_episode_bulk`) per message/document: LLM extracts entities and relations, resolves them against existing nodes, and dates the facts. In the Zep product (v3): `thread.add_messages()` on every chat turn; ingestion is asynchronous and takes seconds-to-minutes ([help.getzep.com](https://help.getzep.com/v2/memory.md)).

**(c) Read path.** Hybrid retrieval fuses **cosine similarity + BM25 full-text + graph traversal (BFS)**, with rerankers: RRF, MMR, cross-encoder, or node-distance from a center node; prebuilt recipes like `COMBINED_HYBRID_SEARCH_RRF`, `NODE_HYBRID_SEARCH_RRF`, `EDGE_HYBRID_SEARCH_EPISODE_MENTIONS` via `search()`/`_search()` ([github.com/getzep/graphiti](https://github.com/getzep/graphiti)). Zep-the-product assembles a ready-made **context block** string — facts and entities with validity date ranges — from the last two thread messages at P95 <200 ms via `thread.get_user_context()`; the earlier `mode="summary"` option is being removed in the February 2026 deprecation wave in favor of one fast structured format ([help.getzep.com/february-2026-deprecation-wave](https://help.getzep.com/february-2026-deprecation-wave), [retrieving-context](https://help.getzep.com/retrieving-context)).

**(d) Consolidation & forgetting.** **Edge invalidation instead of deletion**: when a new fact temporally contradicts an existing edge, the old edge's `invalid_at`/`expired_at` is set to the new edge's `valid_at` — history is preserved, enabling **point-in-time ("as-of") queries** over what was believed true at any date ([neo4j.com blog](https://neo4j.com/blog/developer/graphiti-knowledge-graph-memory/), paper). No summarizing consolidation pass; communities are periodically rebuilt. Fact ratings let retrieval filter low-relevance facts by threshold.

**(e) API surface.** Graphiti: `add_episode`, `add_episode_bulk`, `search`, `_search(recipe)`, `build_communities`; backends Neo4j, FalkorDB, Amazon Neptune (Kuzu deprecated); MCP server + FastAPI REST service included. Zep v3: `user`/`thread` objects, `thread.add_messages`, `thread.get_user_context`, `graph.add`, `graph.search`.

**(f) Steal.** Even without adopting a graph DB, the **bi-temporal columns** (`valid_at`, `invalid_at`, `created_at`, `expired_at`) on a Postgres facts table plus the invalidate-don't-delete rule give auditable memory that matches the ledger philosophy; the **precomputed context block** (assemble once, cache, inject as one string) is the right latency posture for a hot path.

**(g) Weaknesses.** Ingestion is LLM-heavy and slow — Mem0's team measured >600k tokens per LOCOMO conversation and observed facts not retrievable until background processing finished ([dispute coverage](https://agentmarketcap.ai/blog/2026/04/11/agent-memory-architecture-production-2026)); requires a graph database sidecar (violates the three-service constraint unless edges are emulated in Postgres); ontology tuning is real work; benchmark claims are contested in both directions.

## 4. LangMem + LangGraph memory (the native option for this platform)

**(a) Data model.** LangGraph splits memory into **checkpointer** (short-term: full graph state per thread, every super-step, enabling resume/replay/HITL interrupts — `BaseCheckpointSaver`, `PostgresSaver`/`AsyncPostgresSaver`) and **store** (long-term, cross-thread: `BaseStore` items addressed by `(namespace_tuple, key) → value dict`, with `created_at`/`updated_at` and optional vector index) ([docs.langchain.com/oss/python/langgraph/add-memory](https://docs.langchain.com/oss/python/langgraph/add-memory)). Both Postgres implementations ship in **`langgraph-checkpoint-postgres` v3.1.2 (2026-08-07)** ([pypi](https://pypi.org/project/langgraph-checkpoint-postgres/)). Namespaces are hierarchical tuples, e.g. `("memories", user_id)` — the registry/tenancy model maps directly. LangMem layers **memory types** on top: *semantic* (facts — as a growing collection or a single profile document), *episodic* (experiences: situation/thought/action/result), *procedural* (evolving system-prompt rules) ([langchain-ai.github.io/langmem](https://langchain-ai.github.io/langmem/)).

**(b) Write path.** Three sanctioned patterns. (1) **In-the-loop tools**: `create_manage_memory_tool(namespace=("memories", "{langgraph_user_id}"))` + `create_search_memory_tool(...)` — the agent decides what to save/update/delete against the store. (2) **Background manager**: `create_memory_manager(model, schemas=[...Pydantic...], instructions=..., enable_inserts/enable_updates/enable_deletes)` (stateless, returns `ExtractedMemory` list) or `create_memory_store_manager(...)` which additionally searches the store, upserts, and versions automatically (`query_limit=5` default, namespace templates) ([langmem reference](https://langchain-ai.github.io/langmem/reference/memory/)). (3) **Deferred reflection**: `ReflectionExecutor.submit(payload, after_seconds=N)` debounces enrichment until a conversation goes quiet — a background thread, no broker needed, which fits the one-process asyncio constraint.

**(c) Read path.** `store.asearch(namespace_prefix, query="...", filter={...}, limit=n)` — semantic search when the store is constructed with `index={"embed": embeddings, "dims": 1536, "fields": [...]}` (pgvector-backed in PostgresStore; per-item opt-out with `index=False`) ([langchain blog](https://www.langchain.com/blog/semantic-search-for-langgraph-memory)). Inside nodes/tools the store arrives via injected `runtime.store`; hits are formatted into the system prompt by the caller.

**(d) Consolidation & forgetting.** Store-native **TTL**: `TTLConfig(default_ttl, refresh_on_read, sweep_interval_minutes)` — refresh-on-read gives organic decay of unused memories with a periodic sweep ([langgraph TTL how-to](https://langchain-ai.github.io/langgraph/how-tos/ttl/configure_ttl/)). LangMem's store manager reconciles (insert/update/delete against retrieved neighbors, deletions only if `enable_deletes=True`). Procedural consolidation via `create_prompt_optimizer`/`create_multi_prompt_optimizer` (gradient / metaprompt / prompt_memory strategies — from-training for strategy names). For context-window forgetting, LangChain 1.x middleware: `SummarizationMiddleware` (token/message thresholds; 1.1 added an "auto" trigger) ([built-in middleware docs](https://docs.langchain.com/oss/python/langchain/middleware/built-in)).

**(e) API surface & status.** Packages: `langgraph` (1.x line since Oct 2025), `langgraph-checkpoint-postgres` 3.1.2, `langmem` **0.0.30 (2025-10-27)** — pre-1.0, slow release cadence, repo still active post-LangChain-1.0 ([pypi.org/project/langmem](https://pypi.org/project/langmem/)). Also directly relevant to the middleware-first rule: **`langchain-anthropic` ships `StateClaudeMemoryMiddleware` and `FilesystemClaudeMemoryMiddleware`** (Claude's memory tool backed by LangGraph state or local filesystem) plus `AnthropicPromptCachingMiddleware` ([reference.langchain.com](https://reference.langchain.com/python/integrations/langchain_anthropic/middleware/)).

**(f) Steal / build-on.** This is the native substrate, not an inspiration: AsyncPostgresStore keeps truth in Postgres, namespaces give per-user/per-agent scoping, TTL gives forgetting, `ReflectionExecutor` gives ambient-mode consolidation without Celery, and the store is exactly the kind of OOB machinery spec §7.0's precedence rule demands. Treat LangMem as a pattern library to vendor if 0.0.x churn bites; treat the Claude memory middleware as the OOB path to file-style memory.

**(g) Weaknesses.** LangMem is 0.0.x with a ten-month release gap — API stability risk; store search is flat top-k (no graph relations, no temporal invalidation — bi-temporal columns are DIY); checkpointer tables bloat fast without pruning; semantic index config is per-store, so mixed embedding dims require separate stores.

## 5. Anthropic memory tool + context editing; CLAUDE.md as a design school

**(a) Data model.** A **client-side virtual filesystem** under the `/memories` path prefix: plain files (often Markdown/XML) that the client handler maps to any backing store (disk, DB rows, object storage). No schema, no embeddings — organization is directories and filenames; the directory listing itself is the index ([platform.claude.com memory-tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

**(b) Write path.** Model-initiated tool calls; the API is `{"type": "memory_20250818", "name": "memory"}` (now GA, no beta header) with six commands the app executes: `view` (dir listing 2 levels deep, or file with line numbers + `view_range`), `create`, `str_replace`, `insert`, `delete`, `rename`. When the tool is present, the API **auto-injects a memory protocol system prompt**: "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE… ASSUME INTERRUPTION: your context window might be reset at any moment." SDK helpers: `BetaAbstractMemoryTool` / `BetaLocalFilesystemMemoryTool` (Python/TS) run the loop.

**(c) Read path.** Agent-initiated `view` at task start, then targeted file reads — just-in-time retrieval, nothing pre-injected beyond the protocol prompt. Security is on the client: path-traversal validation (`/memories/../../secrets.env` attacks), size caps, sensitive-data stripping — all explicitly documented.

**(d) Consolidation & forgetting.** Three complementary mechanisms: the model itself tidies files (tool description tells it to keep memory organized; docs recommend periodic expiry of stale files); **context editing** — `context_management.edits: [{"type": "clear_tool_uses_20250919"}]` clears old tool results client-side, replacing them with placeholders (beta header `context-management-2025-06-27`); and server-side **compaction** (auto-summarize when nearing the window). Anthropic's internal 100-turn benchmark: memory+context-editing gave **84% token savings and 39% performance improvement** ([context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing), search-verified figures).

**(e) API surface.** As above; plus the documented **multisession pattern**: an initializer session creates a progress log + feature checklist in memory; each later session opens by reading them and closes by updating them — memory as a crash-recovery mechanism.

**(f) The CLAUDE.md school.** Claude Code's memory is files with a **load hierarchy** (managed/enterprise → user `~/.claude/CLAUDE.md` → project `CLAUDE.md` → local), `@path` imports (recursive, max 4 hops, approval on first external import), a `.claude/rules/` directory auto-loaded alongside, and **auto memory**: Claude-maintained notes at `~/.claude/projects/<project>/memory/` where the first ~200 lines/25KB load at session start as an index and topic files (`debugging.md`, `api-conventions.md`) load on demand ([community documentation of the hierarchy](https://alexop.dev/posts/four-types-memory-coding-agents-claude-code/), [guide](https://medium.com/data-science-collective/the-complete-guide-to-ai-agent-memory-files-claude-md-agents-md-and-beyond-49ea0df5c5a9); the `#` quick-add shortcut is from-training — could not be re-verified in current docs). Design theses: memory should be **human-readable and human-editable in place**, versionable in git, with a cheap always-loaded index over lazily-loaded bodies. Letta's MemFS converging on the same shape is independent confirmation.

**(g) Weaknesses.** No retrieval ranking — the model must guess which file matters (fails at large N without a search mod); everything client-side means security and quota enforcement are entirely the client's; unstructured text resists programmatic audit; write quality depends on the model's diligence; per-vendor tool (portable only via the LangChain middleware wrappers above).

**Fit note:** given the platform's rules, the sanctioned integration is `FilesystemClaudeMemoryMiddleware`/`StateClaudeMemoryMiddleware` from `langchain-anthropic` — OOB middleware, but provider-scoped (Anthropic-only), which conflicts with §2.1 provider-agnosticism for a core layer.

## 6. The big products: ChatGPT, Gemini/Vertex Memory Bank, Bedrock AgentCore

**ChatGPT.** Two user-visible layers: **saved memories** (explicit facts written via the internal `bio` tool; user-triggerable with "remember that…") and **reference chat history** (implicit recall over all past conversations, launched 2025-04-10), independently togglable under Settings → Personalization → Memory, with per-memory view/edit/delete in "Manage memories"; deleting chats does not delete memories and vice versa; Temporary Chats bypass both ([openai.com/index/memory-and-new-controls-for-chatgpt](https://openai.com/index/memory-and-new-controls-for-chatgpt/)); memory reached the free tier July 2025 ([axios.com](https://www.axios.com/2025/07/11/chatgpt-memory-update)). Read path (reverse-engineered, not officially documented): everything is **prepended to the system prompt as a dossier** — a "Model Set Context" of saved memories with timestamps, plus hidden sections: *recent conversation content* (timestamped topics, user messages only), *user knowledge memories* (dense periodic summaries), *assistant response preferences* with confidence ratings, and *interaction metadata* (device, usage patterns) ([embracethered.com teardown](https://embracethered.com/blog/posts/2025/chatgpt-how-does-chat-history-memory-preferences-work/), [simonwillison.net/tags/llm-memory](https://simonwillison.net/tags/llm-memory/)). Willison's criticism: an un-inspectable dossier causes **context bleed** into unrelated work. A mid-2026 "Memory Summary" rolling-synthesis update is reported only by low-quality secondary sources — treat as unconfirmed. Product lesson: users need a visible, deletable fact list *and* an off switch per layer; the hidden summarized layers are the part people distrust.

**Gemini / Vertex AI Memory Bank.** Managed service in Agent Engine (GA after 2025 preview): **`GenerateMemories`** runs an LLM **extraction + consolidation** pipeline over session events asynchronously (consolidation merges new facts with existing ones and resolves contradictions), **`CreateMemory`** supports direct/agent-controlled writes; memories are compact facts under a **`scope` dict (exact-match, always including `user_id`)**; retrieval is **`RetrieveMemories`** with embedding similarity (`top_k`) or fetch-all within scope; configurable **memory topics** steer what gets extracted; TTL/expiration and inspectable **revisions** are built in; IAM conditions gate access ([cloud.google.com Memory Bank overview](https://docs.cloud.google.com/agent-builder/agent-engine/memory-bank/overview), [fetch-memories](https://cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/memory-bank/fetch-memories), [launch blog](https://cloud.google.com/blog/products/ai-machine-learning/vertex-ai-memory-bank-in-public-preview)). ADK integration exposes it as preload-at-turn-start or memory-as-a-tool (exact ADK tool names, e.g. `PreloadMemoryTool`, from-training). Notable design: **exact-match scope, not hierarchical prefix** — strict isolation over flexible sharing.

**Amazon Bedrock AgentCore Memory.** Cleanest separation of the three: **short-term** = raw `events` written via `create_event(memoryId, actorId, sessionId, eventTimestamp, payload)` with support for **branches** (fork a session's event history — checkpointing); **long-term** = `memory records` extracted **asynchronously (~1 min)** by **strategies** attached to the memory resource: `SEMANTIC` (facts), `SUMMARY` (running session summary), `USER_PREFERENCE`, and `EPISODIC` (structured episodes: scenario/intent/actions/outcome/reflection, for learning from past successes) ([AWS strategy docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-strategies.html), [semantic strategy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/semantic-memory-strategy.html)). Each strategy owns extraction *and* consolidation prompts (customizable) — consolidation decides whether an insight lands in a new record or merges into an existing one. Records live under **templated hierarchical namespaces** — `/strategy/{memoryStrategyId}/actor/{actorId}/session/{sessionId}/` with trailing slashes to prevent prefix collisions — and **IAM policies can restrict retrieval by namespace path**, giving cryptographically-enforced memory scoping ([memory organization docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-organization.html)). Read: `retrieve_memory_records` (semantic, top-k within namespace) or `list_memory_records` (no search); control plane vs data plane are separate clients. Short-term events carry configurable expiry (order of days-to-a-year; exact default from-training).

**(f) Steal from the products.** ChatGPT: the two-layer UX (explicit editable facts + implicit history reference, separately togglable) is the visibility bar the admin UI should meet. Memory Bank: configurable "memory topics" = a per-tenant allowlist of what extraction may capture. AgentCore: strategy-per-memory-type with its own extraction/consolidation prompts, namespace templates, and permission-checked retrieval — the registry + exposure gates can replicate this exactly in Postgres.

**(g) Weaknesses.** All three are opaque managed pipelines (extraction quality untunable except via prompts/topics); ChatGPT's hidden layers are a trust liability and a prompt-injection persistence vector (memories written by injected content persist across sessions — demonstrated repeatedly by security researchers, from-training); AgentCore's ~1-minute extraction lag means memories aren't immediately queryable; all are cloud-locked, so only their *shapes* transfer to self-hosted.

## TOP 12 TRANSFERABLE MECHANISMS (ranked for a Postgres-first LangGraph platform)

1. **Checkpointer/store split** — keep thread state in `AsyncPostgresSaver` and cross-thread memory in `AsyncPostgresStore` with namespace tuples, never conflating the two (LangGraph).
2. **Debounced background reflection** — queue memory extraction with `ReflectionExecutor.submit(..., after_seconds=N)` after conversations go quiet, giving Mem0/Memory-Bank-style async pipelines inside one asyncio process (LangMem).
3. **Bi-temporal columns + invalidate-don't-delete** — `valid_at/invalid_at/created_at/expired_at` on every memory row so contradicted facts are closed, not erased, enabling point-in-time queries that mesh with the runs ledger (Zep/Graphiti).
4. **ADD/UPDATE/DELETE/NOOP reconciliation** — one structured-output LLM call comparing each candidate fact against its top-k neighbors before writing, as the consolidation gate (Mem0).
5. **Pinned memory blocks rendered every turn** — small labeled rows (`label`, `value`, `limit`, `description`) compiled into the system prompt each turn, with shared blocks across agents via attachment rows (Letta).
6. **Sleep-time/dreaming agents as ambient mode** — idle-time subagents that re-read recent runs and rewrite blocks/facts, with the HITL gate as the "review before applying" step (Letta; mirrored by AgentCore's async extraction).
7. **Strategy-typed memory with per-type namespace templates** — semantic/summary/preference/episodic strategies, each with its own extraction+consolidation prompt and a namespace like `/strategy/{id}/actor/{id}/`, permission-checked at retrieval (Bedrock AgentCore).
8. **Precomputed context block** — assemble facts+entities into one cached string at write time and inject it in <200ms instead of running retrieval in the hot path (Zep v3).
9. **File-style memory via OOB middleware** — `FilesystemClaudeMemoryMiddleware`/`StateClaudeMemoryMiddleware` for human-readable, git-versionable agent notes, satisfying the middleware-precedence rule with zero custom code (Anthropic memory tool × langchain-anthropic).
10. **Index-file-over-topic-files loading** — always load a small memory index (first N lines) and lazy-load topic files on demand, keeping the tree visible as navigation (Claude Code auto-memory; Letta MemFS `system/` pinning).
11. **TTL with refresh-on-read** — `TTLConfig(default_ttl, refresh_on_read=True, sweep_interval_minutes)` so unused memories decay organically while touched ones survive (LangGraph store).
12. **User-visible memory ledger** — an admin-UI list of every memory with view/edit/delete, per-layer toggles, and a mutation history table, because the products converged on this and the hidden-dossier alternative is the most criticized design in the field (ChatGPT UX + Mem0 `history()`).
